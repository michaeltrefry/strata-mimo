# MiMo-V2.6-Flash-RL: expert routing on coding text

Measured 2026-10-07 to decide whether 4-bit (MXFP4) experts can reach 80+ tok/s output on one RTX PRO 6000
(96 GB) with the rest of the experts in RAM.

## How it was measured

- `tools/mimo/moe-trace.cpp` (built inside llama.cpp `5ad1c5d` as `examples/moe-trace`) records the 8 experts each of
  the 47 MoE layers picks for every token, teacher-forced, on GPU 0.
- **Coding answers:** the model's own answers (with reasoning) to 44 coding prompts (write, debug, explain, agent
  tasks), generated by `tools/mimo/gen_answers.py` at temperature 0.7: 49,151 tokens. This is what generation sees.
- **Code corpus:** 68 source and doc files from local repos: 167,867 tokens. This is what pasted files and prompts
  look like.
- `tools/mimo/analyze_trace.py`: profile from the even-numbered documents, tested on the odd ones (out of sample).
- Budget: 6,609 experts (12.75 MiB each) = 82.3 GiB, what GPU 0 has left at 256K context with 8-bit KV, Q8_0
  attention and the MTP head. 54.9% of the 12,032 experts.
- Traces and texts: `E:\strata-mimo\traces` (480 MB).

## Share of expert choices served from the GPU at that budget

| Profile from -> tested on | Static profile | Per-layer LRU, same size |
| --- | ---: | ---: |
| coding answers -> other coding answers | 84.7% | 92.5% |
| code corpus -> other code files | 80.5% | 91.8% |
| both -> answers / code | 82.0% / 80.1% | - |
| answers -> code corpus | 76.3% | - |
| code corpus -> answers | 78.3% | - |
| answers, +200 experts (5-bit attention) | 85.8% | - |

Other numbers: 25 (answers) and 5 (code) of the 12,032 experts were never chosen. Two consecutive tokens use 13.6-13.9
different experts of the 16 they pick per layer, so a 2-token MTP verify reads almost twice the experts.

## Estimated output speed (not measured)

One token reads 4.68 GiB of MXFP4 experts. With the GPU (attention + resident experts, ~1.6 TB/s effective) and the
CPU (missed experts, 90-120 GB/s) working in parallel and 1 ms of other time per token, no drafting:

| GPU hit rate | 90 GB/s CPU | 120 GB/s CPU |
| ---: | ---: | ---: |
| 76% | ~70 tok/s | ~90 tok/s |
| 80% | ~84 tok/s | ~109 tok/s |
| 85% | ~105 tok/s | ~130 tok/s (GPU-bound) |

## Design decisions from this

- Base the resident set on a profile of generated coding answers, plus a dynamic part that adapts to the current
  session (LRU stays above 91% on both kinds of text).
- 4-bit experts can clear 80 tok/s if the CPU path reaches ~90+ GB/s and the hit rate stays at 80%+.
- MTP drafting gains only where the extra experts are already on the GPU.

## CPU speed for the experts in RAM (measured)

`tools/mimo/mxfp4-cpu-bench.cpp` (built in llama.cpp as `examples/mxfp4-cpu-bench`): the real MXFP4 experts of 24
MoE layers (76.5 GiB) copied into ordinary RAM (4 KiB pages), then per token 47 layers x M random experts: gate+up,
SiLU, down, rows split over all threads, three barriers per layer. llama.cpp's stock `ggml_vec_dot_mxfp4_q8_0`
(AVX-512), one token at a time. Threadripper 9960X, 4 x 128 GB DDR5-6400 (205 GB/s peak), Windows 11.

| Experts per layer | 24 threads | 48 threads |
| ---: | ---: | ---: |
| 1 | 6.39 ms/token, 98.4 GB/s | 6.25 ms, 100.6 GB/s |
| 2 | 12.51 ms, 100.5 GB/s | 13.99 ms, 89.8 GB/s |
| 3 | 19.56 ms, 96.4 GB/s | 189.16 ms, 10.0 GB/s |
| 4 | 24.58 ms, 102.2 GB/s | 93.02 ms, 27.0 GB/s |
| 8 | 45.40 ms, 110.7 GB/s | 38.55 ms, 130.4 GB/s |

- One thread per core: with 48 threads the spinning barriers break down when Windows puts two on one core.
- ~100 GB/s is half the RAM's peak; 130 GB/s with more experts in flight says more is there. To try in the engine:
  multi-token AVX-512 kernels, large pages, prefetching the next layer's experts.
- At 100 GB/s the estimate is ~90 tok/s at an 80% GPU hit rate and ~110 tok/s at 85% (no drafting).
